## Temporary firmware

`esp32dev_mpu6050_check` compiles only `src/Mpu6050Check.cpp`, using Arduino
Wire and no new external libraries. It does not run CAN/DHT or publish motion
data, and does not alter the normal 0.4.0 applications or their version/schema.
Uploading it replaces the sensor application until the combined image is
explicitly restored. Dashboard firmware must not be replaced by this target.

Every two seconds on SDA21/SCL22 at 100 kHz, with a 25 ms transaction timeout:

- Read MPU register 0x75 (WHO_AM_I) at address 0x68; report ID_MATCH only for
  0x68, otherwise ID_MISMATCH. AD0 does not change the expected identity byte.
- Independently read INA219 register 0x00 at address 0x40 and print its two-byte
  configuration. The value depends on reset/previous settings; a complete read
  is communication evidence, not unique identity or calibrated measurement.
- Report register-selection errors, short reads, and initialization failure;
  never substitute a success value. Reads select register pointers only, with
  no reset/wake/configuration/calibration data writes and no full address scan.

Example desired output, not an observed result:

```text
#mpu6050_check,address=0x68,status=ID_MATCH,who_am_i=0x68
#ina219_check,address=0x40,status=REGISTER_READ,config=0x399F
```

## Acceleration/tilt stage — deployed, magnitude discrepancy under review

The separate `esp32dev_mpu6050_measure` target compiles only
`src/Mpu6050Measure.cpp`. The communication target remains unchanged. No CAN
application version, protocol, schema, or source flag changes are made. This
stage does not implement the CAN vibration field or a condition percentage.
Operator build and upload succeeded; the sensor now runs this measurement
diagnostic, with dashboard USB unplugged by instruction. It is not currently
running a CAN-publishing application.

Unlike the communication-only check, this program resets/configures the MPU:
awake PLL X-gyro clock, all axes enabled, no FIFO/DMP/auxiliary master,
SMPLRT_DIV 9, CONFIG 3 (44 Hz accelerometer bandwidth), ACCEL_CONFIG 0x08
(+/-4 g, 8192 counts/g), gyro self-test off, and DATA_RDY enabled. INT remains
physically unconnected; the status register is polled. Nominal internal rate
is 100 Hz; the displayed stream deliberately waits at least 200 ms after each
attempt and does NOT retain all samples, guarantee 5 Hz output, compute RMS,
or provide anti-aliased vibration analysis. INA219 is not read or configured;
it stays physically attached. CAN and DHT tasks remain disabled.

Every displayed HW_SAMPLE requires checked identity/settings before and after
a six-byte acceleration burst. The program clears pending INT_STATUS and then
waits for a new DATA_RDY bit, with a rollover-safe 50 ms polling budget (not a
whole-acquisition deadline). Wire timeout is 25 ms per transaction. Checked
big-endian signed conversion yields axis acceleration and Euclidean magnitude
in g, including gravity. It rejects incomplete reads, wrong identity/settings,
reset-not-complete, data-ready timeout, and axis values within eight counts of
the signed full-scale rails. Failures print a reason and four NaNs, never an
old/numeric substitute. Genuine numerical zero remains numerical zero.
After communication/settings/freshness failures, a later paced attempt resets
and reconfigures the MPU; this behavior is not yet physically validated.

`include/Mpu6050Diagnostic.hpp` supplies the actual conversion/rail/timeout
helpers plus compile-time assertions for signed boundaries, +/-1 g/zero,
profile bits, and timeout rollover. The successful operator MCU build evaluates
these assertions. The existing 66 host tests pass but do not execute this
driver or its C++ assertions. PlatformIO parsing confirms both targets are isolated
from each other and from the unchanged default/combined application flags.

With both USB supplies unplugged, build only:

```powershell
platformio run -e esp32dev_mpu6050_measure
```

Do not upload until this succeeds. Upload only to the separately identified
physical sensor with dashboard USB unplugged. Then monitor at 115200 baud.
The numeric format is:

```text
mpu6050_measure,t_ms,HW_SAMPLE,ax_g,ay_g,az_g,norm_g
```

First observe the module stationary on a nonconductive support without exposed
pins touching contacts: magnitude should be roughly 1 g, not zero, because
gravity is included. Later gently tilt by holding its edges without pulling
wires or touching exposed pins. Axis components should redistribute and settle
with magnitude roughly 1 g. Do not shake, drop, hit, or add a motor. Record actual
values before claiming that response. This is a basic gravity/tilt plausibility
check, not calibrated accuracy, vibration RMS, or CAN scheduling/fault validation.

Profile reference also checked against [Adafruit's MPU6050 driver 2.2.6](https://raw.githubusercontent.com/adafruit/Adafruit_MPU6050/2.2.6/Adafruit_MPU6050.cpp);
no Adafruit motion dependency was added or source copied from Project 1.

## Controlled pose capture — no calibration changes

`tools/capture_mpu_pose.py` is a non-flashing host tool for this diagnostic's
seven-field serial records. After a pose has settled, close the monitor and
capture 15 seconds on the identified sensor port. It sets DTR/RTS inactive
before opening and never writes serial commands, MCU configuration, or correction
constants. It saves exact `raw.log`, all parsed valid/explicit-unavailable
records in `samples.json`, and `summary.json` with counts, per-axis/norm mean,
population standard deviation and ranges. Each capture gets a unique ignored
`data/mpu-pose-<UTC>-<pose>-<random>/` directory, not a replacement of prior data.

Example (COM8 is an example, not a permanent sensor identity):

```powershell
py tools/capture_mpu_pose.py --port COM8 --pose z_up --seconds 15
```

Run that relative script from the project directory. Other supported pose
labels are z_down, x_up, x_down, y_up, y_down. Labels describe the operator's
intended orientation, not verified level/axis geometry. Start with chip side up
on a level, nonconductive support, pins clear and no pressure on the chip; keep
wires relaxed and the board stationary. Remove meter probes before positioning.
Do not change any wiring while powered or connect dashboard USB for this test.
Opposite/static poses will be requested separately after inspecting each result.

Result RECORDED means sufficient usable data without detected recording issues,
never sensor-accuracy PASS. All captures say accuracy NOT_VALIDATED. Explicit
failures remain counted after recovery; malformed/nonfinite/inconsistent-norm
records, sparse coverage, long device intervals, timestamp resets/duplicates,
interrupted captures, and port errors require REVIEW. Initial partial lines
are retained and count malformed if unparseable; a final incomplete line is
retained raw but excluded from sample statistics. Repeated same-valued readings
with advancing device timestamps are not proof of frozen data or freshness;
there is no diagnostic sequence/session or physical pose attestation.

No offset/gain correction, per-vector normalization, or calibration fit is
performed. Do not tune numbers to force a 1 g norm. The current discrepancy
needs controlled evidence and a separate decision before integration.

78 host tests pass: the preceding 66 plus 12 parser/collector/averaging and
fake-serial capture tests, including failure retention, signed/zero values,
bad numeric fields/UTF-8, timestamp rollover/reset, fragments, unique captures,
inactive controls before open, and preservation of a 0.87 g mean without
normalization. These do not run the MPU driver or validate physical pose data.
