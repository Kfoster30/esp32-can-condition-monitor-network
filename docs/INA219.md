## Logic wiring, power off before changes

| INA219 | Sensor ESP32 (the board connected to DHT11) |
|---|---|
| VCC | Its own 3V3 |
| GND | Its own GND |
| SCL | GPIO22 / D22 |
| SDA | GPIO21 / D21 |
| VIN- and VIN+ | Initially disconnected for the communication check; later LED branch below |
| Green measurement terminals | Empty when the duplicate VIN header pins are used |

Keep existing CAN/DHT connections unchanged. Never tie the two ESP32 3V3 outputs
together. No battery, external supply, or motor is part of these stages. The
measurement branch is only the sensor's own 3V3 / resistor / LED circuit below.
Labels, not wire colors, define the connections.

## Separate detection-only build

`esp32dev_ina219_check` compiles only `src/Ina219Check.cpp`. It uses the bundled
Arduino Wire library, SDA21/SCL22, 100 kHz, a 25 ms transaction timeout, and
address 0x40. It selects register 0x00 and requests its two configuration bytes
every two seconds; it writes no configuration or calibration register values.
Only the register pointer is selected. It does not scan other device addresses.

This is a temporary diagnostic replacement for the physical sensor's application,
not an INA219-enabled CAN firmware. It does not run CAN or the DHT task. Therefore
the dashboard will time out if powered alongside it. The diagnostic does not
alter the application wire layouts or its hardware-source labels. SIM and
DHT-only application modes still simulate voltage/current; prepared 0.4.0 adds
a separate combined hardware target. Restore an appropriate application build
after diagnostic work; do not perform the healthy CAN soak on this target.

Build only (no board power or upload required):

```powershell
platformio run -e esp32dev_ina219_check
```

Operator screenshots confirmed a successful build and hash-verified sensor-only
upload of this communication target, followed by repeated
`#ina219_check,address=0x40,status=REGISTER_READ,config=0x399F` on COM8.
This completes the basic communication check, not measurement acceptance.
Identify the sensor physically and its port separately before any upload; keep
the dashboard disconnected during that upload. Monitor the sensor's own serial
port at 115200 baud, DTR/RTS inactive, after a successful upload.

Expected communication result:

```text
#diagnostic=INA219_WIRING_CHECK,revision=1
#role=SENSOR_DIAGNOSTIC,can_enabled=0,dht_enabled=0
#ina219_check,address=0x40,status=REGISTER_READ,config=0x399F
```

0x399F is the documented power-on configuration, not a unique identity register.
Another complete value is recorded for review, not silently declared defective.
REGISTER_READ establishes only a completed two-byte transaction at the expected
address. It does not establish sensor accuracy, shunt calibration, correct load
placement, or real voltage/current delivery over CAN. Register-select errors,
short reads, and initialization errors are printed explicitly instead.

## Resistor-limited LED branch — operator assembly and observation

The operator measured the loose resistor as 0.331 kilohm (331 ohms), supplied
`IMG_7015.jpeg` / `IMG_7016.jpeg`, and clarified the obscured connections:

1. Sensor 3V3 -> INA219 VIN+ (white wire).
2. INA219 VIN- -> resistor (another white wire).
3. Other resistor end -> red LED anode.
4. LED cathode -> sensor GND (green wire).

The photos do not independently resolve every hidden breadboard contact. The
path is based on the operator's explicit trace; duplicate white wires must not
be distinguished by color alone. The operator subsequently powered only the
sensor and reported that the red LED lit. This demonstrates branch conduction,
not correct current-sense routing, shunt calibration, or meter agreement.
Never connect VIN- directly to 3V3 or GND or bypass the resistor/LED path. Keep
both boards unplugged for wiring changes; the dashboard stays unplugged during
the standalone diagnostic. The 331-ohm resistor is an operator measurement,
not a nominal-value assumption or a photographed calibrated-meter record.

## Separate measurement build — manual bench observations recorded

`esp32dev_ina219_measure` compiles only `src/Ina219Measure.cpp`, using bundled
Wire and the same SDA21/SCL22 / 100 kHz / address 0x40. It does not run CAN or
DHT. The original communication target remains available and unchanged.
The source programs nominal R100 calibration 8192 (50 microamp/current LSB)
and configuration 0x019B: 16 V bus range, +/-40 mV shunt range, 12-bit ADCs,
triggered shunt-and-bus conversion. These are scaling settings, not permission
to apply external voltage/current; the only authorized branch remains 3V3/331
ohms/red LED. No new libraries are required.

Each acquisition writes calibration/configuration, waits for conversion-ready
with a 50 ms polling budget and 25 ms I2C transaction timeout, then reads shunt,
current, and setting readbacks. The polling budget is not a strict whole-sample
execution deadline because I2C calls can block. Read/write/short-read errors,
conversion timeout, wrong settings, overflow, and out-of-bench-range values
produce explicit unavailable rows (`nan`), never retained or simulated numbers.
The diagnostic rejects bus above 5 V, current outside +/-12 mA, or shunt rail
values at/beyond +/-40 mV. These are software screening bounds, not protection.
Negative in-envelope current is preserved for polarity/offset investigation.

Pure conversion/classification helpers have compile-time assertions in
`include/Ina219Diagnostic.hpp`. The operator reported successful build and upload
of this target, followed by the runtime output described below. The build
evaluates these assertions; no measurement-build terminal screenshot or exact
duration was supplied. Existing Python codec/capture tests do not execute the
I2C driver.

Build only, both boards unplugged:

```powershell
platformio run -e esp32dev_ina219_measure
```

After successful build and separately directed sensor-only upload, the output
format is `ina219_measure,t_ms,status,bus_V,current_mA,shunt_mV`. `HW_SAMPLE`
means successful checked register acquisition, NOT a measurement-accuracy PASS.
Bus voltage means VIN- relative to common ground; current is the LED branch,
not total ESP32/USB current. No expected numeric sample is fabricated here.

### Manual measurement and fault-check results

| Check | Observation |
|---|---|
| Loaded readings | HW_SAMPLE, 3.328–3.332 V, 4.1–4.3 mA, 0.410–0.430 mV shunt |
| Meter at VIN- relative to sensor GND | Operator reported 3.31 V; difference from displayed INA219 range 0.018–0.022 V |
| Meter across measured 331-ohm resistor | Operator reported 1.41 V; derived current 4.2598 mA, within the displayed loaded range |
| Open LED load | After power-off opening of VIN--to-resistor connection, HW_SAMPLE 3.332–3.336 V and -0.1 to 0.0 mA |
| Load restored | After power-off restoration, screenshot shows 3.328–3.332 V and 4.2 mA |
| SDA disconnected | After power-off removal of only module SDA, repeated WRITE_FAILED,nan,nan,nan |
| SDA restored | After power-off restoration and sensor-only reboot, operator reported return to expected readings; no new screenshot supplied |

The reference formula is `I_mA = 1000 * V_resistor / 331`; no ammeter was placed
across the supply or resistor. Readings were manually reported/screenshot-based,
not synchronized logged comparisons. Meter model, calibration, uncertainty,
environmental control, and repeated reference trials were not established.
The approximately 0.02 V difference and agreement with the 4.26 mA reference
support this low-energy bench demonstration, not a traceable accuracy claim.
The 4.1–4.3 mA values span different displayed samples; selecting a single one
does not establish a precise percentage measurement error.

Opening the load and disconnecting SDA are different tests: the former produced
numeric near-zero current, while the latter produced unavailable values, not
zero or retained numeric data. All intentional wire changes were performed with
both USB supplies disconnected. Recovery was checked after power cycling, not
by live hot-plugging or within a measured continuous recovery interval.

The initial loaded screenshots contain garbled/repeated serial text, including
repeated partial timestamps. Later no-load, restored-load, and missing-SDA
windows look readable. The cause has not been identified, and a clean saved
raw-serial stability capture has not yet verified its absence. Do not diagnose
the display, USB link, or firmware as its proven cause from screenshots alone.

[0.4.0 CAN integration](INA219_CAN.md) defines power source/validity semantics and
separate worker scheduling. Operator builds passed, application uploads were
reported successful, and a new 600-second healthy combined CAN capture passed
with both hardware channels available and sequence checks clean. The physical
sensor has now been reported flashed with the combined application instead of
this standalone diagnostic. Integrated loss/recovery and reset acceptance remain
pending. SIM and DHT-only modes still simulate power; old 0.3.0 evidence is not
relabeled as the new integration test.
